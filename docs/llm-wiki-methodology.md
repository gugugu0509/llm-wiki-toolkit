# LLM Wiki 方法论：让 AI 持续维护一个知识库

> 一句话：**知识被「编译」一次并持续保鲜，而不是每次提问时临时拼凑。**
> 这是与 RAG 的分野——RAG 每次检索原始片段，LLM Wiki 维护一份**已经写好、持续修订**的 wiki。

本文是这个工具包的方法论部分，与 `append_only_guard.py` / `chunked_asr.py` 配套。

---

## 一、四层结构

| 层 | 目录 | 谁拥有 | 规则 |
| --- | --- | --- | --- |
| **原始来源** | `raw/` | 人 | **不可变**：你策展的文章、论文、图片、转录。AI 只读不改 |
| **Wiki** | `wiki/` | AI | **全权维护**：实体页、概念页、来源摘要、综合（evolving thesis）、索引 |
| **运维元数据** | `_meta/` | 共同 | **入库版本化**：自检脚本、告警日志、生成器 |
| **时间线** | `wiki/log.md` | AI | **append-only**：每次 ingest/query/lint 追加一行，可 grep |

三条设计红线：

1. **`raw/` 只进不改** —— 原始材料一旦入库就不再编辑，修订发生在 `wiki/` 层。这样任何时候都能回答「这个结论是从哪来的」。
2. **`index` 与 `log` 是共享文件** —— 多个 AI（或多人）会同时写，冲突概率最高。提交时**只提交自己那一行**（path-limited commit），改完立即 commit，避免工作区脏着去跑别的任务。
3. **数字不手写** —— 页面里的计数（「共 N 条」）应由生成器产生或由自检脚本对账；手写数字必然滞后。

## 二、三个工作流

### 1) ingest（摄取）

```
放来源进 raw/  →  AI 读来源  →  写来源摘要页（wiki/sources/）
                              →  更新相关实体页 / 概念页
                              →  修订综合页（wiki/overview.md）
                              →  登记 index.md、追加 log.md
                              →  跑自检（见下）→ 有问题先修再提交
```

要点：**ingest 的收尾必须有一道自动校验**。字段缺失、计数滞后、断链、index 漏登记这几类问题会**反复**出现，靠人记不住——这正是 `append_only_guard.py` 之外的「自检脚本」存在的理由。

### 2) query（提问）

```
先读 index.md 定位  →  读相关页面（而不是全文检索原始材料）
                   →  带引用的答案
                   →  好的答案归档回 wiki（这是知识库长大的主要方式）
```

要点：**答案要带引用**（指向 `wiki/` 页或 `raw/` 来源）。没有引用的综合容易变成「不可追溯的断言」。

### 3) lint（体检）

定期让 AI 检查：

| 检查项 | 想抓的问题 |
| --- | --- |
| frontmatter 完整性 | `type` / `updated` / `status` 等字段缺失或值不在值域内 |
| 日期格式 | `updated` 不是 `YYYY-MM-DD` |
| 计数对账 | 页面声明的条数 ≠ 实际块数 |
| 断链 | `[[页面]]` 指向不存在的页（要排除日志里的历史链接） |
| index 覆盖 | 内容页没登记进 index |
| 无入链页 | 孤儿页面（没有任何页面链到它） |
| 页内重复标题 | 同一个 `##` 标题出现两次（通常是一次编辑事故） |
| **纯追加护栏** | 本轮「只加不删」的改动里出现了删除行（见下） |
| git 工作区 | 提交前是否干净、改动范围是否符合预期 |

## 三、`--append-only` 护栏：本工具包最实用的一个设计

**它解决的事故**：一次「只加不删」的批量编辑（补字段、加注记、互指），实际却删掉了东西——
因为脚本把某一行当作**替换锚点**，而那一行本身是需要保留的内容。

**为什么结构自检抓不到**：删掉一行之后，标题层级、链接、计数**可能全都还是对的**。
只有逐字回读才能发现，人力成本高且容易漏。

**判据（机器可验、成本近零）**：

```bash
python append_only_guard.py          # 工作区未暂存改动
python append_only_guard.py --cached # 已暂存改动
```

内部就是 `git diff --numstat`：**每个改动文件的「删除列」必须为 0**。
非 0 就 FAIL，并逐个文件列出 `+N/−M`，要求编辑者**逐字说明删了什么、为什么**。
二进制文件（numstat 里以 `-` 表示）自动跳过。

> 实践建议：把这一步做成**提交前的门禁**（pre-commit hook 或 CI 的一步），
> 而不是靠自觉。它不是为了提高标准，而是为了**挡住一整类「以为在追加、实际在替换」的事故**。

## 四、多 AI（或多 Agent）共用一份知识库

当两个以上的 AI 维护同一个目录时，需要写成显式契约：

1. **开工前**看 `log.md` 尾部和 `git status`——知道上一个人做到哪、有没有半成品。
2. **一人一主题**：同时改同一页面必然冲突。
3. **改完即 commit**，并且消息里注明执行方（谁做的、依据是什么）。
4. **追加优先于改写**：需要修正时以「补注」形式追加，保留原文（这样历史判断也能被追溯）。
5. **共享文件（index / log）只提交自己那一行**。

---

## 五、为什么值得这么做

| 做法 | 收益 |
| --- | --- |
| `raw/` 不可变 + `wiki/` 可持续修订 | 结论可追溯，且能演进 |
| log.md 只追加 | 时间线可 grep，跨机器可追溯 |
| 自检脚本入 `_meta/` | 门禁可复现，不依赖某台机器上的临时脚本 |
| 计数不手写 | 消除最常见的「文档撒谎」形态 |
| 纯追加护栏 | 把一整类编辑事故变成机器可挡 |

---

## 六、这个工具包的边界

- 只包含**平台无关**的能力：文档编辑护栏、本地音频转写。
- **不包含**任何内容抓取、平台客户端模拟、cookie 管理、签名绕过等代码——那些既依赖具体平台，
  也涉及平台协议与第三方权利，不适合放进一个公开工具包。
- 方法论部分不含任何第三方材料；`raw/` 里放什么由你自己决定，请自行确认来源与授权。
